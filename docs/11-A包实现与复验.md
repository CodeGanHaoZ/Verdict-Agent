# A 包 v0.1：接入、运行与复验

实现范围：共享协议、以太坊账户状态核验、EIP-712 归属、证据构造与独立复验 CLI。没有实现 B/C 的服务目录、后端、网页、存证、模型或主网部署。

## 1. 安装和运行

使用 `.nvmrc` 固定的 **Node 22.23.3、npm 10.9.9**；`.npmrc` 会拒绝不满足 engines 的运行时。安装 Node 后，在仓库根执行：

```bash
npm ci --ignore-scripts
npm run typecheck
npm test
npm run demo:a
npm run verify -- .local/a-demo/bundle.json --context .local/a-demo/trusted-context.json --json
```

构建后也可调用工作区 CLI：

```bash
./node_modules/.bin/z-verify .local/a-demo/bundle.json --context .local/a-demo/trusted-context.json
```

`npm run demo:a` 每次生成新的本地演示签名，故证据摘要可以不同。它使用已保存的真实链上证明并要求完整验收为 PASS 才导出；不会查询网络，也不启动服务。可在命令后追加输出目录，例如 `npm run demo:a -- .local/second-export`。

`bundle.json` 是规范化证据正文；`manifest.json` 保存 Keccak 摘要；`trusted-context.json` 是本示例生成、需要调用者自行审阅并接受的检查点与密钥配置。**不能因为别人同时提供了这三个文件，就自动信任其上下文。** CLI 要求显式 `--context`，不会从证据包推导信任授权。

开发机曾将官方 Node 下载到被忽略的 `.local/node-v22.23.3-linux-x64/`；该目录不随 Git 分发。如果本机 shell 仍默认 Node 18，可在当前 shell 设置 `PATH="$PWD/.local/node-v22.23.3-linux-x64/bin:$PATH"`；其他机器应自行安装 `.nvmrc` 所指定的官方运行时。

## 2. 给 B/C 的稳定入口

四个 npm workspace 是 `@verdict/protocol`、`@verdict/core`、`@verdict/evidence`、`@verdict/verifier-cli`，均通过公开入口消费。运行时 schema／类型在 `packages/protocol/src/index.ts`；`schemaVersion=1.0.0`，`ruleVersion=eth-account-v1`。

| API | 实际签名与行为 |
| --- | --- |
| `verify_delivery`，core | `await verify_delivery(request, delivery, context)` → VerificationResult；不联网、读文件或数据库 |
| `request_digest`，core | 请求通过严格 schema 后，以 JCS+Keccak 摘要绑定完整任务，包括 requestId、字段、政策、有效期和预算 |
| `delivery_typed_data`，core | 从 DeliveryEnvelope 构造固定域与类型的 EIP-712 payload；B 可以用所选签名库签署，不必再写一套摘要规则 |
| `build_evidence`，evidence | `await build_evidence(request, delivery, context, provenance)` → `{bundle, manifest}`；内部实际核验，不接受调用者自报 verdict |
| `replay_evidence`，evidence | `await replay_evidence(bundle, manifest, context)` → ReplayResult；重新核验并对比报告 |
| `fact_key`，evidence | `await fact_key(bundle, context)`；先核验可归属交付，再按语义事实分组，不按 requestId 或重复签名计票 |
| `canonical_json` / `parse_json_strict`，protocol | 规范化／严格解析，拒绝重复键、非 JSON、非法 Unicode 和过大输入 |

B/C 所需的请求、响应、上下文、检查行、结果、证据、manifest、复验结果 schema 与枚举已经导出；具体 Candidate、RunSnapshot 的业务字段仍由 B 在共享协议中对齐，A 没有实现其业务状态机。

`VerificationResult` 的 `verdict`、`dataVerdict`、`attributionStatus`、`attributableFailure` 分别有独立语义。供 C 展示的 `checks` 包含要求、实际值、状态、原因与包内证据定位。对于缺失材料，定位指向本应存在的位置；不能将这种缺失当作已证实存在的材料。

## 3. 当前协议的明确取舍

- 首个数据链只支持 Ethereum mainnet 1。使用固定版本 EthereumJS 的主网硬分叉编码，并检查该分叉必需的头字段，不能用库的默认值补齐缺失字段后给通过。
- 请求的账户字段为 balance、nonce、codeHash、storageRoot。金额和整数使用 uint256 十进制字符串；地址／字节串使用小写十六进制；nonce 等 RPC 数量在适配边界转成十进制。验证所有请求字段，也检查响应额外提供的账户字段。
- 不存在账户只有在 MPT 返回有效不存在证明后才采用零余额、零 nonce、零哈希占位；已存在空账户按实际 RLP 值核对。其他提供商的不存在表示需要显式适配，不能悄悄修改已签署的响应。
- 支持 `signed-account-v1` 和 `proof-only-v1` 两个政策。前者同时要求数据通过和授权签名；后者可以接受已验证但无签名的数据，归属仍为 UNSIGNED。调用方不能改变已命名政策的含义。
- 签名域固定 name、version、32 字节 salt；identityChainId 与数据链分别绑定。签名覆盖服务／版本、requestHash、responseHash、交付状态、数据链、区块与有效期。响应摘要包含证明与区块头，不能在签署后替换或删除材料。
- 调用方提供可信检查点、有效密钥绑定、评估时间与时间来源。历史复验使用明确的历史评估时间，回答“在当时条件下能否通过”，不意味着该交付今天仍可重新采用。
- live 模式检查 consumedRequestIds；B 必须在实际执行层原子地维护请求消费状态。无状态核验函数不会替调用方持久化 nonce，也不自动解决并发重放。
- 同一材料、同规则、同上下文可逐项复现。换用上下文会返回 CONTEXT_DIFFERENT 并给出新上下文下的重算结果，不能冒称原报告一致。
- 可信基准、共识最终性、身份控制者及交付时间的真实性仍是外部信任前提，不从证据包里的自报字段推导。

## 4. 证据完整性和退出码

摘要定义为 `keccak256(UTF8(JCS(bundle)))`。正文不含自身哈希、可变下载地址或未来交易引用。大整数用字符串，非法代理项、重复键、非有限数及不安全整数均拒绝。CLI 文件上限 2 MiB，解析嵌套层数和证明节点／单节点大小有上限；schema 有错是输入错误，缺少支持的证明材料则按结果返回未知。

重新计算哈希只证明取得了同一份内容。即使攻击者修改报告后重新计算摘要，重跑签名、证明与请求规则仍会发现差异。报告者文字与采集来源的陈述没有因此自动获得真实性保证。

| CLI 退出码 | 含义 |
| --- | --- |
| 0 | 完整性 VERIFIED、报告 MATCH、重新验收 PASS |
| 2 | 报告复验一致，但该交付的真实验收结论是 FAIL |
| 3 | 无法核验、未知规则／schema、UI_MOCK，或调用者上下文不同 |
| 4 | 文件摘要不符，或重算结果／基准声明与原报告不符 |
| 1 | 文件不可读取、语法／schema 无效、重复键或用法错误 |

CLI 默认在 bundle 同目录读取 manifest.json，可通过 `--manifest` 指定。调用者自行加载可信 context，不读取第一实例 DB、不联网。独立进程表示复验不依赖原进程结果缓存，不代表独立组织背书。

## 5. 实际样本与测试范围

使用 [以太坊 26134149 样本](https://github.com/hankesong/Verdict-Agent/blob/code/fixtures/core/ethereum-mainnet-26134149/README.md)：9 节点 WETH 存在证明和 8 节点不存在证明，保存原始证明及头字段。采集工具可按同一高度重新只读获取原始材料；网络证明窗口失效不影响已保存样本的离线复验。

测试包括真实区块头／MPT／字段／本地适配器签名，以及错块、错值、无效或缺失签名、未知授权、错误身份链、过期、请求重放、缺材料、截断证明、基准冲突、最终性政策不足、未知规则、重复 JSON 键和篡改。

CLI 测试把导出的三份文件复制到另一个临时目录，删除原导出目录，再启动新的 Node 进程核验；同时检查删除文件、篡改但不改摘要、改正文后重算摘要等情况。测试不依赖在线 RPC，不启动 B/C 模块。

这些结果证明 A 包的固定案例与所覆盖边界已可运行，不能外推为所有区块、协议、身份或服务可靠性已验证。依赖及许可证见 [THIRD_PARTY](https://github.com/hankesong/Verdict-Agent/blob/code/THIRD_PARTY.md)。
