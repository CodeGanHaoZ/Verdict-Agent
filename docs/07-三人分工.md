# Verdict — 三人分工与联调计划

2026-10-06。用户要求将当前方案拆为三个人的工作包。成员姓名与专长未指定，以下用 A／B／C 表示岗位；可直接按能力认领。工作包与接口是本次交付，表中的实现任务尚未完成。

## 1. 三个人各自交付什么

| 负责人 | 工作包 | 适合的能力 | 最终必须交出的东西 |
| --- | --- | --- | --- |
| A | [验收内核、证据格式与复验工具](work-packages/A-验收内核与复验.md) | TypeScript、以太坊证明／签名、测试 | 正常／错块／错值／未知可区分的验收库，证据包与独立复验 CLI |
| B | [服务接入、任务流程与后端](work-packages/B-服务接入与后端.md) | 后端、Agent 工具调用、数据与联调 | 三个签名演示服务、真实观测、候选排序、预算内替换、API 和独立实例配置 |
| C | [审计界面、存证与演示](work-packages/C-审计界面与存证.md) | 前端、EVM 基础、产品演示 | 三个真实接线的界面、最小本地存证模块、可重走的演示与交付说明 |

A 对“为什么这个结果能通过／拒收”负责；B 对“任务能否从输入跑到结束”负责；C 对“用户能否看懂依据并复查”负责。**B 担任联调负责人，A 担任验收规则负责人，C 担任演示与交付负责人。** 这是工作分配建议，不是已联系或已指派给某个真实成员。

三个人一起保住同一条主线：提出任务 → 选服务 → A/B 错误交付被拒收 → C 正确交付通过 → 展开审计依据 → 下载证据 → 第二实例复验 → 下一次选择变化。这里的演示服务 A/B/C 与人员编号无关，实现时建议命名为 `demo-wrong-block`、`demo-wrong-value`、`demo-valid`，避免混淆。

## 2. 代码目录与共享文件负责人

以下是拟议目录，不代表这些代码已经存在。不复制原仓库的反事实实验或 PI 上游源码。

```text
packages/protocol/         A：共享类型、JSON schema、枚举
packages/core/             A：基准、签名、证明、字段与规则检查
packages/evidence/         A：规范化、摘要、证据构造与事实分组
apps/verifier-cli/         A：从文件重跑核验
fixtures/core/             A：公开来源的证明向量和期望结果

apps/server/               B：任务状态、选择／替换、HTTP API、存储与发布队列
services/demo/             B：三个签名演示服务，签名格式调用 A 的共享定义
packages/observations/     B：真实端点观测、指标与能力记录
examples/consumer/         B：最小工具调用示例（模型接入仍为 P1）
scripts/dev/               B：启动、独立实例和联调脚本

apps/web/                  C：选择、单次审计、证据与复验三个视图

packages/anchor-client/    C：发布适配器，交由 B 的队列调用

```

根 `package.json`、workspace 配置、锁文件、CI 与统一启动入口由 B 维护；A/C 把依赖需求交给 B 或单独提交小改动，避免三人同时重建锁文件。共享 schema 由 A 维护，API 路由及运行状态由 B 维护，界面状态解释由 C 对照共享枚举消费。

采用技术设计中的 TypeScript 方向；具体 Node 版本、包管理器、证明库和前端工具在启动时一次固定。PI 仍是后续适配，不以魔改上游为前置条件。

## 3. 先交接口和样本，再并行实现

建议启动后的第一个小时用于共同确认 [接口约定](08-接口约定.md)，不是等核心开发结束才讨论格式。

| 先交的东西 | 提供方 → 消费方 | 作用 |
| --- | --- | --- |
| `TaskSpec`、`DeliveryEnvelope`、`VerificationResult`、`EvidenceBundle` | A → B/C | 全部使用同一套字段、枚举和原因码 |
| 正常、错块、错值、未知的**界面形状样本** | A/B → C | C 可立即做页面；标记为 UI_MOCK，不算已通过真实证明校验 |
| 任务、候选、证据、复验、发布状态的 HTTP 草案 | B → A/C | 前端 mock 与后端实现遵守同一个约定 |
| 第一个真实可核验账户样本与检查输出 | A → B/C | 尽早替换界面样本，暴露真实数据接线问题 |
| 存证适配器签名与 receipt 格式 | C → B | B 可先用明确返回“未接入”的适配器跑通核心流程 |

初始数据先按共享 schema 校验；仅 schema 通过不能标成密码学核验通过。未接入真实验证器时，任何演示结果都保留 UI_MOCK 标识，不能进入公共证据索引或发布队列。

## 4. 阶段门槛与工作顺序

用协同启动时刻 T 计算，下面是检查点建议，不是假定当前还剩 38 小时，也不是对工期的保证。B 在启动时记录实际提交期限和可用时长，安排至少最后 6 小时联调、演示与材料准备。

| 阶段 | A | B | C | 全队退出条件 |
| --- | --- | --- | --- | --- |
| G0：T+约 1h，约定格式 | schema、枚举、函数边界 | workspace、API 草案、启动约定 | 页面字段核对、mock 消费 | 同一份任务与结果可被三人读取；不强绑已实现状态 |
| G1：优先争取 T+约 4h，技术关卡 | 一个真实样本通过，错块／错值被拒收，原始证据可看 | 演示服务骨架、一次真实观测、运行状态 API | 三个视图消费统一样本 | A/B 能真跑一份签名交付；C 能直接替换同结构数据 |
| G2：开发窗口前半段，首次纵向联调 | 签名与未知负例、证据导出 | 自动切换到合格服务，失败停止，API 接通 | 展示真实任务和证据引用 | “错误拒收 → 换服务 → 通过”经过真实内核，不存在页面硬编码结论 |
| G3：功能冻结前，公共复验 | CLI 重跑与篡改检查 | 第二实例、证据导入、固定输入的排序对照 | 复验状态、对照展示、本地存证与失败分支 | 第二实例重算且采用适用证据；本地存证失败不改写验收结论 |
| G4：最后至少 6h，交付 | 修复核验问题、补规则与版本说明 | 全新环境运行、集成修复、运行命令 | 全路径演示、链接与状态核对、交付材料 | PRD 对应用例有实际结果；失败项明确记未完成 |

G1 若基准、证明或签名无法跑通，B/C 优先协助定位依赖与输入，延后存证拓展和视觉润色。不能用模型打分、固定返回 PASS 或只展示 mock 越过技术关卡。主网工作线仅在网络、费用和交易授权具备时进入执行，不能挤占联调缓冲。

| PRD 项目 | 主责 | 协作／验收 |
| --- | --- | --- |

验收由负责成员先给实际运行证据，再由另一成员重走关键路径。第二实例可复用同一确定性核心，但不能读取第一实例的数据库或直接采用它的 result 标签。独立进程不等于独立组织背书。

## 6. 合并与联调约定

- 建议各自使用 `feat/verifier`、`feat/orchestration`、`feat/audit-ui` 分支；名称只是建议，本次没有创建或分派分支。
- 首批先合入共享 schema 与工程入口，再按小步骤合入，不等三人全部做完再合并。
- 共享字段变更先记录在接口文档并通知另外两人；破坏性变化更新 schemaVersion 或 ruleVersion，不能悄悄改字段含义。
- B 维护联调问题表；哪个模块负责的问题由谁修，B 负责把完整流程接回去。
- 只提交明确选择的文件。私钥和真实 API 凭据留在被忽略的本地配置；示例密钥运行时生成。真实运行证据先审阅再决定是否公开。
- 任何人都不能为赶进度把未知改成通过、把冻结样本标成实时、把本地部署称为主网部署。

## 7. 时间不够时保什么

优先保住可信单笔验收、失败替换／停止、逐项审计、证据导出、第二实例复验与选择变化。减少真实端点数量、页面动画和非关键统计，记录未完成的需求；不能删除真实观测后仍声称 FR-05 完成。

PI／模型、完整 SDK/MCP、支付、复杂抗女巫与其他候选场景不加入此次 P0 工作包。存证先完成最小本地验证；不能因主网延期阻塞可运行核心，也不能把延期项算作完成。
