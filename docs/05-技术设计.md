# Verdict — 验收与证据审计技术设计

融合设计 v0.2 · 2026-10-06 · 以下为拟议实现约束，尚未完成运行验证

[产品需求](02-PRD.md)规定用户行为与完成标准；本文解释支撑这些行为的机制。配套 [架构图](03-架构设计图.svg) 与 [交互图](04-交互设计图.svg) 均为设计示意。

## 1. 模块与职责

| 模块 | 职责 | 为什么独立 |
| --- | --- | --- |
| 任务与验收条件 | 固定目标、字段、证据策略和预算 | 防止交付后临时降低要求 |
| 目录、观测与选择 | 区分声明／实测能力，解释候选顺序 | 可用性和数据正确性需要不同依据 |
| 确定性验收核心 | 基准、签名、证明、字段与条件检查 | 模型和服务评分不能改写核验结论 |
| 审计报告 | 关联承诺、实际交付、检查结果与证据 | 用户能看到接受／拒收的具体理由 |
| 证据与复验 | 版本化材料、摘要、规则重跑及适用性 | 消费者可以独立验证报告中的断言 |
| 存储与发布 | 本地索引、下载、可选异步摘要锚定 | 链上故障不阻塞本地数据验收 |
| 宿主适配 | 最小调用接口；后续 PI、SDK/MCP 接入 | 工具层不依赖某一家模型或框架 |

采用 TypeScript 分层方向，计划使用 SQLite 索引、内容寻址证据文件和一个网页；具体库及版本在最小验证中固定。当前 A 包及必要运行工程已实现，见 [A 包说明](11-A包实现与复验.md)；B/C 应用与数据库尚未实现。职责与依赖方向仍按 [工程结构](09-工程结构.md)。

## 2. 一次审计记录的结构

每次调用保存以下逻辑对象，字段名为 schema 草案：

| 对象 | 必需信息 |
| --- | --- |
| `request` | 数据链、账户、目标区块、字段、签名要求、请求 ID、有效期、预算 |
| `service` | 服务 ID、版本、端点标识、身份命名空间与密钥绑定依据 |
| `delivery` | delivered／unsupported／rejected、请求摘要、响应内容、签名 |
| `baseline` | 目标区块头、状态根、来源、确认策略、适用网络与规则 |
| `checks` | 检查 ID、要求、实际值、证据引用、PASS／FAIL／UNKNOWN／NOT_APPLICABLE／NOT_COVERED |
| `result` | 主 verdict、数据结论、归属状态、原因码及处理动作 |
| `provenance` | 采集者、时间、实时／冻结／故障注入标签、依赖版本 |

`checks` 组成审计对照表；`result` 由核心按版本化规则推导。报告者或模型提供的文字只能引用这些对象，不能自己填一个 PASS 使材料通过。

NOT_APPLICABLE 必须有规则依据；NOT_COVERED 表明未检查，不是安全保证。模型对自由文本承诺的提取应保留原文并供确认；首版实际判定限定在已确认的结构化请求，不宣称能自动证明任意自然语言承诺。

## 3. 独立基准与账户证明

验收依赖一个显式选择的区块基准，而不是让被检查服务同时任意提供答案和判定标准。

1. 通过明确的独立策略取得数据链和目标区块哈希，记录来源、最终性要求及信任前提。
2. 按对应网络和硬分叉规则编码区块头，重算哈希并匹配目标。缺少必要头字段或不支持编码时返回无法核实。
3. 从匹配的头中取得 `stateRoot`，核验账户地址对应的 MPT 路径及存在／不存在证明。
4. 解码账户记录，比较 nonce、原生币 balance、storageRoot、codeHash 与交付字段。
5. 检查网络、账户、字段、区块及请求语义，不因证明自洽就忽略任务不匹配。

哈希一致证明头与目标哈希相符，不独自证明目标属于规范链或已最终确认。多源比对用于发现冲突，不能将多数一致直接升级成密码学保证。

查询尽可能固定 `blockHash`；EIP-1898 及 `eth_getProof` 的具体组合支持需逐个提供商测试。若仅能按高度查询，必须检测查询间区块变化并明确限制；不能静默改变目标。proof window 限制、归档可用性与近期状态能力分别记录。

账户不存在时验证相应证明并采用明确的返回约定，不把缺失数据随意补成零。账户证明包含 storageRoot 不等于已验证具体存储槽；codeHash 也不能直接说明源代码已审计或合约整体安全。

## 4. 签名、归属与重放

计划使用 EIP-712，绑定服务 ID／版本、请求摘要、数据链、目标区块、交付状态、响应摘要和有效期。签名域由协议定义版本与应用边界，身份链和数据链分别存储，不能混用 chainId。

验签之外，还需明确：

- 请求 ID、重复响应接受规则、有效期及跨任务重放防护；EIP-712 本身不自动防重放。
- 服务签名密钥的授权来源、有效版本、轮换和撤销记录。元数据里任意声明一个地址不足以完成绑定。
- delivered、unsupported 和 rejected 的不同语义；拒绝请求不等于交付了承诺数据。
- 演示适配器为自己的响应签名，只能证明该适配器的交付，不能冒充底层公共 RPC 提供商签名。

P0 可用可信配置固定演示身份及密钥映射，复验者需要接受该配置的来源；不得把证据包自己携带的一份未经认证的映射当成独立授权证明。标准注册表接入后应保存可回溯到交付时的有效绑定，不能只查询当前可变元数据。

签名中的时间戳是签署方声明；如需证明实际交付时间，须补充可信的时间或记录依据。历史复验区分“当时是否满足有效期”与“现在能否重新用于新请求”；旧包过期后仍可研究，但不能重新授权当前调用。

## 5. 判定、采用与公开反证

数据检查、服务归属、文件完整性、发布状态是不同维度。任一维度不能代替其他维度。

- 数据符合所需检查，且所有必需证据门槛满足，才输出主结果 PASS。
- 已确定的条件不符导致 FAIL；未能判断的项仍保留 unknown，不因总结果而消失。
- 未签名但证明有效的数据可以被核查。要求签名的任务仍不采用；允许未签名的任务须在调用前显式选定策略。
- 有效服务签名、明确请求绑定、适用规则及支持该项失败的基准齐备时，才能发布“该服务签署了这份不合格交付”的限定反证。
- 签名无效、归属不明、超时、限流或单方日志，不据此公开断言被声称的提供商交付了错误数据。

失败原因决定补材料、复检、换服务或停止。模型不得放宽必需条件、把未知变通过，或用不可核查的推测替代缺失的证据。

## 6. 真实观测、指标与排序

小规模探针记录目标、方法、区块范围、时间、请求结果、时延、错误码和采集者。声明能力与实测能力分开；窗口限制不是证明错误，429 不表示永久不支持。

指标按任务分组，显示样本数和窗口，不混合冻结样本、人工故障与真实观测。未知、失败和未交付原因不能从分母中悄悄删除；不假定重复请求独立，也不根据小样本承诺整体可靠性。

排序规则版本化：先检查硬条件，再检查适用历史证据与复检要求，再参考本地观测，最后以延迟或已知价格处理同等条件。默认不汇聚陌生观察者的可用率；新服务为未知，不因为无历史被永久排除。去掉历史证据后的对照必须固定其他输入。

## 7. 证据包、规范化与摘要

拟采用版本化 JSON schema，规范化方式以 RFC 8785 为候选，并通过正式实现与测试向量验证。大整数使用约定的十进制字符串；地址、哈希和字节串使用固定的小写十六进制表示与长度校验；缺省和 null 的语义固定。禁止重复键和不符合 schema 的值，不能只靠排序键、删除空格来声称规范化完成。

建议使用两个层次：

```text
bundle.json                  不可变证据正文，包含请求、响应、证明、版本和检查记录
manifest.json                evidenceHash、文件位置、可选发布者签名与锚定引用

evidenceHash = keccak256(UTF8(JCS(bundle)))
```

正文不包含自身 `evidenceHash`、可变下载位置或后来生成的交易哈希，避免循环摘要和发布后内容变化。EIP-712 响应签名摘要、证据文件摘要与事实分组键分别定义；服务签名不对一个含自身签名的对象循环求哈希。

证据正文可包含报告者的原始检查结果供对照，但复验器必须重新计算。摘要一致只证明取得了同一份字节内容；若攻击者修改正文又重算摘要，独立签名／证明／条件检查仍应能发现可检查的不符。

事实分组依据服务身份与版本、规范化语义请求、目标区块、规则和核验事实。报告者地址、请求随机数、重复转发和签名表示不增加权重。分组用于抑制重复事实放大，不宣称识别独立真人或所有关联身份。

## 8. 第二实例复验

另一实例执行：获取文件 → 核对规范化与摘要 → 校验 schema／规则版本 → 选择并检查自身接受的基准与身份策略 → 重做签名、证明和任务检查 → 比较逐项结果 → 判断历史事实对当前任务是否适用。

`z-verify <bundle> --context <trusted-context.json>` 已作为 A 包 CLI 实现，支持逐项报告及 JSON 输出。安装与退出码见 [A 包说明](11-A包实现与复验.md)；调用者必须自行接受外部可信上下文。

材料不可取、规则不支持、身份历史不完整或基准策略不接受时显示无法复验，不读取原报告的 PASS 作为替代。某些检查可基于固定材料离线完成，最新规范链状态、在线身份解析或当前服务能力则可能需要联网。

第二进程和独立数据库用于证明流程不依赖第一实例的结果缓存，不等于独立组织背书；不同钱包地址也不证明不同主体。

## 9. 公共索引、异步存证与身份关联

SQLite 保存服务目录、观测、调用索引和发布队列，内容寻址文件保存完整证据。公开记录区分观察报告和可归属签名交付。索引可以采用稳定的审计记录 ID，但不使用“已获 CVE 编号”之类暗示官方认定的表述。

计划中的发布状态为 not_requested／pending／confirmed／failed，与 verdict 和复验状态独立。链上拟记录 evidenceHash、schemaVersion、发布者及可选身份命名空间、文件获取提示；发布者提交的结论仍是声明，不是合约已执行证明验证。

数据链以以太坊为首个场景；身份链和注册表待选择并验证；BOT Chain 为拟议摘要锚定链。三者明确标识，跨链引用不等于跨链共识验证。主网网络、ABI、Gas、浏览器和费用在采用前核实；本次没有部署或发送交易。

ERC-8004 是身份与反馈的接入候选。实际支持字段、版本、签名密钥授权和反馈来源过滤须以选定部署为准。其注册不保证能力真实，反馈人数不自动增加正确性；不强行把三态验收压成缺乏语义说明的分数。

先逐份摘要锚定；批量交易优化、小时 Merkle 根与多点镜像后置。链上摘要既不保证内容真实，也不保证链下文件长期可取。服务修复时发布关联的新检查，保留旧记录的版本和适用条件。

## 10. 最小消费接口与 Agent 边界

下表保留业务接口设计；A 包实际已实现的核验／证据函数签名见 [实现说明](11-A包实现与复验.md)，B/C 编排与发布尚未实现，尚无已分发 SDK：

| 接口 | 语义 |
| --- | --- |
| `find_service(task, constraints)` | 返回候选、能力依据和排序理由 |
| `check_service(serviceId, task)` | 有预算的探测；区分新观测和历史记录 |
| `verify_delivery(request, response)` | 确定性核验与审计行，不接受模型自报结果 |
| `verify_before_use(task, candidates)` | 组织选择、调用、核验和有界替换；无通过交付就停止 |
| `report_outcome(bundle)` | 验证材料后入索引，按策略进入发布队列 |
| `replay_evidence(evidenceId)` | 下载并重跑检查，返回适用范围与差异 |

模型负责需求理解、工具选择和解释；可以建议补证据，不可以自行执行任意代码或改变检查规则。一个轻量循环足以验证流程时，如实展示为工具演示。PI 和完整 MCP 适配作为 P1；不为抓取、证明校验和摘要计算分别增加大模型。

## 11. 扩展到其他审计场景的边界

已有讨论中的安全助手、DAO 承诺对照、升级／审计覆盖检查、反事实调查，可复用任务定义、证据引用、版本与未知项、报告和复验框架。它们需要各自的执行模拟、源码映射或实验基线，账户状态证明不能直接替代。

本稿先把服务交付验收讲清楚；这些候选既不作为当前实现成果，也不因被讨论或试验而自动取代本次设计。
