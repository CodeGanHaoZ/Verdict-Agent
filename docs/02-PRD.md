## 1. 用户、问题与产品目标

主用户是需要消费外部链上状态的 Agent 应用开发者。次用户是希望解释交付边界和修复情况的服务方；公共证据消费者包括其他 Agent 实例、研究人员和审计人员。

| 用户面对的情况 | 系统应如何帮助 | 首版边界 |
| --- | --- | --- |
| 不清楚服务是否支持历史账户证明 | 区分声明能力、实测支持、未知与范围限制 | 少量真实端点；不保证覆盖所有服务 |
| HTTP 成功但区块或字段不符 | 依据指定区块、证明和请求拒收 | 只覆盖所支持的账户字段 |
| 有错误响应却无法证明是谁提供的 | 分开记录数据检查与服务归属 | 观察者日志不充当服务方签名 |
| 想重用他人的经验 | 下载材料、重验、检查适用性，再调整顺序 | 不把报告数量换算成统一信誉分 |
| 所有服务都未满足要求 | 停止该数据依赖，说明缺失条件 | 不静默采用未验收数据 |

成功标准是让调用者知道本次数据能否采用、为什么以及如何复查。原稿列举的商业服务事故未逐案核实，暂不作为产品效果证明。

## 2. 首个支持的任务

任务是生成指定以太坊区块的账户状态事实卡。请求至少包含：

- 数据链 `chainId`、账户地址和目标 `blockHash`。
- 字段白名单：原生币 `balance`、`nonce`、`codeHash`；按需展示账户的 `storageRoot`，不验证任意存储槽。
- 证据策略：是否要求有效服务签名、采用哪种区块基准与最终性策略。
- 请求 ID、有效期、最多候选数、超时及成本预算。

固定历史任务精确匹配区块哈希；近期任务先固定参照区块与最终性条件，再执行同样的验收。基准不可确定则返回无法核实。ERC-20 `balanceOf`、任意 `eth_call`、完整事件列表和合约漏洞判断不在此字段白名单内。

## 3. 核心用户流程

1. 用户或宿主 Agent 提交任务，确认区块基准与证据策略。
2. 系统展示候选能力、观测来源、指标窗口与排序理由；排除已知不满足硬条件者，未知能力可有限探测。
3. 调用受控签名服务 A，发现区块不匹配；拒收并保存证据。
4. 调用受控签名服务 B，发现响应余额与有效账户证明不一致；拒收并保存证据。
5. 调用服务 C，所有必需检查通过，产出状态事实卡。事实卡保留区块、字段和证据引用。
6. 独立展示真实 RPC 的观测：支持、范围限制、限流或失败；真实结果如实呈现，不要求现场发生故障。
7. 输出证据包及轻量公共索引；计划中的异步锚定显示实际发布状态。
8. 第二实例使用独立进程和存储下载证据、重跑规则，再判断其对当前任务是否适用。
9. 对照启用／停用同一份适用证据时的候选顺序和理由；新顺序仍须执行当前验收。

另设必演分支：候选耗尽、整体超时或超预算时停止数据依赖。第二实例复验说明可重复执行，不自动证明操作者或基础设施独立。

## 4. 结果模型与页面用语

### 4.1 审计对象与逐项结论

一次验收审计记录包括服务身份与版本、请求条件、明确接受的交付要求、实际响应、核验规则、证据与后续动作。服务简介只作为能力声明，不能被当成已履行事实；`unsupported` 或 `rejected` 也不能当作接受了本次交付承诺。

| 报告列 | 例子（设计示例） |
| --- | --- |
| 约定／检查要求 | 指定区块 X 的账户余额，并提供证明与有效服务签名 |
| 实际交付 | 响应绑定了区块 Y，且其账户证明有效 |
| 检查与依据 | 请求条件、两个区块哈希、签名响应、区块匹配检查 ID |
| 逐项结论 | 区块不符；Y 下的值可核查；无法据此回答 X 下的余额 |
| 处置 | 拒收本次交付，保存适用范围，预算内换服务 |

报告区分「满足要求」「已证实不符」「无法核实」「不适用」「未覆盖」。不适用或未覆盖不计作通过；必需条件不能被模型改成不适用以绕过验收。身份、来源和规则缺口需要明确列出，结论不得从“这次交付不符”扩张成“整个服务不可信”。

### 4.2 主结果与独立维度

界面主结果 `verdict` 表示**是否满足本次请求的必需条件**：

| 主结果 | 含义 | 后续行为 |
| --- | --- | --- |
| `PASS` | 本次所有必需条件已经验证通过 | 输出数据，保留适用范围 |
| `FAIL` | 已确定至少一项必需条件不符 | 拒收，预算内换服务 |
| `UNVERIFIABLE` | 材料、基准、身份或规则不足以完成判断 | 不采用；允许补材料或换服务 |

内部必须同时保存 `dataVerdict`、`attributionStatus`、`deliveryStatus`、`reasonCodes` 与 `artifactIntegrity`。主结果不是服务声誉判决。

| 示例 | 数据检查与归属 | 典型主结果及归责 |
| --- | --- | --- |
| 有效签名、基准明确、证明和字段全部通过 | 数据 PASS，归属 VERIFIED | PASS |
| 有效签名下返回错误区块或证明支持的值与响应矛盾 | 数据 FAIL，归属 VERIFIED | FAIL，可形成限定条件的交付反证 |
| 未签名，但账户证明通过 | 数据 PASS，归属 UNSIGNED | 要求签名时 UNVERIFIABLE；显式允许未签名时可 PASS，仍不可声称已证明提供者归属 |
| 未签名且字段与有效证明矛盾 | 数据 FAIL，归属 UNSIGNED | FAIL 并拒收，不能形成针对所称服务的可归属反证 |
| 签名无效或密钥授权不明，其他检查通过 | 数据 PASS，归属 INVALID 或 UNRESOLVED | 要求归属时 UNVERIFIABLE，不推断该服务造假 |
| 明确返回不支持目标历史范围 | 未取得可检查交付；UNSUPPORTED | UNVERIFIABLE，能力记录，不归责 |
| HTTP 429、超时、基准冲突或材料缺失 | 分别记录 RATE_LIMITED、TIMEOUT、BASELINE_CONFLICT、EVIDENCE_MISSING | UNVERIFIABLE，不把临时限制当永久不支持 |

有确定性不符时可拒收，即使其他检查未完成；但形成可归属反证还需要有效服务签名、明确请求绑定、适用规则和支持该项失败的可信基准。无法核验的项目逐项保留，不能用总结果掩盖。

## 5. 功能需求与优先级

### P0：建议的最小完整流程

| 编号 | 需求 | 可检查的输出 |
| --- | --- | --- |
| FR-01 | 请求条件与固定基准 | 请求校验、区块头来源、最终性策略和规则版本 |
| FR-02 | 账户证明与字段验收 | 区块头哈希、MPT 证明、账户解码与字段逐项结果；不含存储槽扩展 |
| FR-03 | 服务身份与签名 | EIP-712 域、请求响应绑定、有效期与重放规则；最小可信密钥映射 |
| FR-04 | 三个受控演示服务 | 错块、错值、正确交付，明确标注故障注入 |
| FR-05 | 真实观测与能力目录 | 少量端点的实际响应或限制，附来源、时间、条件与样本数 |
| FR-06 | 多维指标与简单排序 | 能力、结果计数、延迟、区块匹配、已知成本和证据状态；排序可解释 |
| FR-07 | 有限替换与停止机制 | 次数／时间／预算上限；没有通过的数据就停止该依赖 |
| FR-08 | 证据包与轻量索引 | 版本化 schema、规范化字节、内容摘要、下载及重复事实分组 |

| FR-10 | 审计报告、最小消费接口与页面 | 承诺—交付—证据—处置对照、宿主无关调用接口、演示调用方及三视图 |
| FR-11 | 本地／测试环境锚定验证 | 摘要记录与发布状态分离，失败不阻塞已完成的本地验收 |

FR-05 建议先观察 2–3 个端点，数量不是对网络可用性的保证。若无法取得真实观测，明确记录阻塞，该项不能用冻结样本替代后标成完成。FR-03 首版可使用可信配置固定演示密钥；该配置属于显式信任前提，不能冒充已完成 ERC-8004 注册。

FR-10 的 P0 只要求一个最小调用集成。`z-guard` 是沿用初稿的暂定接口名称，“一行调用”是集成目标，不包含安装、身份和基准配置；完整 SDK 和 MCP 双形态不同时作为首版硬门槛。

## 6. 指标与候选排序

服务卡展示支持状态、PASS/FAIL/UNVERIFIABLE 的数量、未交付原因、本地可用性、延迟、区块匹配、已知报价和证据适用范围。任何比例都附分子、分母、采样窗口、任务类别和采集来源；未测显示未知，超时不记零延迟，限流不记证明错误。

排序顺序：满足硬条件 → 检查相关历史证据与复检要求 → 参考近期本地观测 → 在同等条件下比较延迟和已知成本。输出明确原因，不产生未定义的全局信誉总分。

相同事实的转发、地址数量和重复成功不增加证据权重。历史失败不永久封禁；服务修复后的当前交付可以通过。默认不汇总陌生报告者的超时日志来惩罚真实提供商。

## 7. 三个主视图

| 视图 | 用户应能看到什么 | 必须处理的分支 |
| --- | --- | --- |
| 选择服务 | 请求条件、能力来源、多维指标、排序与理由 | 未测、明确不支持、无候选、预算不足 |
| 单次任务 | 调用时间线、承诺／交付对照、逐项证据、未知和未覆盖项、处置与事实卡 | 错块、错值、材料缺失、全部失败停止 |
| 证据与复验 | 下载材料、规则版本、复验结果、排序对照、发布状态 | 包不可取、被修改、规则不支持、基准策略不接受、锚定失败 |

来源标签至少包括实时观测、冻结样本、故障注入。未实现的发布、复验或模型集成显示未接入；示意图不得作为已运行截图使用。

## 8. 非功能要求

- **确定性与可复查**：同一材料、规则及显式基准策略得到一致结果；策略不兼容时报告差异，不伪造一致。
- **安全**：验签之外定义重放边界；限制请求目标、响应大小、证明节点数、文件大小与执行时限。下载器仅接受允许的地址协议并防止访问内部服务。
- **隐私**：公共证据仅使用审阅过的公开任务材料，不包含 API 密钥、私人查询或认证 URL。
- **性能**：记录核验耗时、证据体积、重试次数和实际费用；“数秒内完成”是待测目标，不是已测指标。
- **可用性**：网络不通可查看明确标注的已有样本；证据包足够时可离线重验相关检查，在线身份解析或基准确认的依赖必须列明。
- **发布隔离**：本地核验状态与锚定状态分别保存；摘要锚定失败不改写数据结论。

## 9. 完成标准与负例

以下为全产品验收标准。A 包已运行与其相关的正常／负例及独立 CLI 检查，具体范围见 [A 包说明](11-A包实现与复验.md)；自动替换、网页与链上分支不能据此标成完成。

| 编号 | 场景 | 期望行为 |
| --- | --- | --- |
| AC-01 | 有效基准、签名、证明和请求 | PASS，事实卡与证据字段一致 |
| AC-02 | 有效签名，但目标区块不符 | 拒收；正确的历史目标本身不被误判陈旧 |
| AC-03 | 有效签名，余额与有效证明不符 | FAIL，第二实例复现相同原因 |
| AC-04 | 修改原签名响应再投诉 | 无效签名可见；不归责于被冒名服务 |
| AC-05 | 证明通过但无服务签名 | 数据 PASS；根据请求策略决定采用，归属保持未证明 |
| AC-06 | 不支持、429、超时、基准冲突、缺材料 | 原因分别展示，无误报的可归属交付反证 |
| AC-07 | 全候选失败或预算耗尽 | 明确停止数据依赖；不输出伪通过事实卡 |
| AC-08 | 第二进程、独立存储复验原包 | 重做摘要、签名、证明与请求检查，报告完整适用范围 |
| AC-09 | 包被篡改、不可获取或规则未知 | 完整性失败或无法复验；不沿用原 PASS 标签 |
| AC-10 | 开关一份适用反证，其余输入固定 | 候选顺序／复检理由有可解释变化；当前验收仍执行 |
| AC-11 | 重复转发相同证据／修复后再交付 | 不增加权重；新交付可通过，旧记录保留适用范围 |
| AC-12 | 真实观测和模拟故障并存 | 来源、窗口、样本数分开，能力与限流不混淆 |
| AC-13 | 本地／测试环境发布失败 | 验收结论不变，发布状态失败；主网未部署如实显示 |

第二进程不等于独立主体背书。完整抗女巫机制、端到端性能和实际链上费用需各自评测，不从以上用例外推。

## 10. 推进门槛与交付清单

正式开发按「共享协议与运行工程 → 基准与证明 → 签名与负例 → 观测与排序 → 导出与第二实例复验 → 页面与演示」推进。模型、支付或链上交易不能替代核心验证。

当前按用户要求拆为三人协作，具体职责和依赖见 [三人分工](07-三人分工.md)。早期材料中的 solo 与剩余 38 小时仅为历史规划记录；不表示当前团队规模或剩余时间。启动实施时重新核实可用时间，建议至少保留最后 6 小时用于联调与交付。

最终代码交付应包括固定依赖与运行说明、来源清楚的样本、真实验收记录、可下载证据及复验命令、可运行页面和演示材料。若完成主网部署，再附网络、地址、交易和浏览器链接；未完成则如实标注。

当前实际交付包括文档、A 包和 B 后端闭环可运行实现；网页与真实链上模块仍待完成。赛事归类、主网配置、费用、提交入口和官方要求均需在实际采用前核实。
