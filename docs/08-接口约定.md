# Verdict — A/B/C 接口约定

2026-10-06。用于三份 [工作包](07-三人分工.md) 对齐。A 包共享请求、交付、可信上下文、检查、结果、证据和复验 schema 已冻结为 1.0.0，实际定义在 `packages/protocol/`。B 的业务对象与下文 HTTP 路由已实现，API_VERSION=1.0.0；C 简易网页已接入，真实存证适配仍待接入。实际 B 运行及扩展路由见 [B 实现](13-B包实现与复验.md)。实际 A 包函数和差异见 [实现说明](11-A包实现与复验.md)，依赖方向见 [工程结构](09-工程结构.md)。

## 1. 统一数据语义

链上大整数使用十进制字符串；地址、哈希、字节串按 schema 约定的长度和小写十六进制编码。时间字段使用统一格式并注明其来源，服务自报时间不当成可信时间证明。A 证据对象带 schemaVersion，规则带 ruleVersion；B 业务快照使用 apiVersion，嵌套对象沿用共享 schema。

| 对象 | 最小字段与语义 | 负责人 |
| --- | --- | --- |
| `TaskSpec` | requestId、dataChainId、account、blockHash、fields、evidencePolicyId、validity、budget | A 定义，B/C 消费 |
| `VerificationContext` | 独立区块基准及其来源／策略、授权密钥的有效版本、评估模式／时间依据、ruleVersion；由调用者可信配置提供，不能仅相信包内自报值 | A 定义，B 获取并组装 |
| `DeliveryEnvelope` | serviceId、serviceVersion、requestHash、deliveryStatus、response、可选 signature 及签名域；服务接受并绑定的请求条件必须可核对 | A 定义，B 的服务产生 |
| `VerificationResult` | verdict、dataVerdict、attributionStatus、reasonCodes、checks、ruleVersion；不包含链上发布结果 | A 产生 |
| `CheckResult` | checkId、requirement、actual、status、reasonCode、evidenceRefs；材料引用可解析到包内对应对象 | A 产生，C 展示 |
| `EvidenceBundle` | request、service、delivery、baseline、checks、result、provenance 与版本；不含自身 evidenceHash 或可变交易引用 | A 构造，B 保存 |
| `EvidenceManifest` | evidenceHash、schemaVersion、bundle 获取位置、可选发布者签名和发布引用 | A 定义，B/C 补外围状态 |
| `Candidate` | serviceId、version、declaredCapabilities、observedCapabilities、metrics、source、metrics 内的 windowStart/windowEnd/sampleCount、rankingReasons | B 产生 |
| `RunSnapshot` | runId、status、task、candidates、attempts、accepted（serviceId/evidenceId/blockHash/values 或 null）、stopReason、createdAt/startedAt/finishedAt | B 产生 |
| `ReplaySnapshot` | replayId、status、evidenceId、contextId、result（含 artifactIntegrity/recomputedResult/comparison/reasonCodes）、reportConsistent、error | B 管生命周期，A 产生重算结果 |
| `AnchorReceipt` | status、evidenceHash、可选 chainId／contract／txHash／blockHash／error；仅实际 confirmed 时给确认依据 | C 定义，B 保存 |

`artifactIntegrity` 在下载／复验层计算并随 ReplaySnapshot 或证据详情返回，不由不可变正文自证。`deliveryStatus` 保留在交付对象及其运行快照，主结果和交付状态不能混用。

## 2. 枚举必须统一

| 维度 | 值 | 注意 |
| --- | --- | --- |
| verdict / dataVerdict | PASS、FAIL、UNVERIFIABLE | 取值相同但语义不同；verdict 还受本次证据要求影响 |
| attributionStatus | VERIFIED、UNSIGNED、INVALID、UNRESOLVED | 数据通过不代表归属已经证明 |
| deliveryStatus | delivered、unsupported、rejected | 超时和 HTTP 429 属于调用观测原因，不能伪造服务签署的拒绝 |
| check.status | PASS、FAIL、UNKNOWN、NOT_APPLICABLE、NOT_COVERED | 必需项不能被改为未覆盖后仍主结果通过 |
| provenance.mode | LIVE、FROZEN、FAULT_INJECTION、UI_MOCK | UI_MOCK 仅用于界面开发，不得发布成真实验收记录 |
| run.status | QUEUED、RUNNING、SUCCEEDED、STOPPED、ERROR | SUCCEEDED 必须有实际通过的交付；STOPPED 包括候选耗尽／预算结束；ERROR 用于流程本身异常 |
| replay.status | QUEUED、RUNNING、COMPLETED、ERROR | COMPLETED 表示复验流程结束，不表示数据 PASS；预期的完整性失败或无法复验也可完成并附原因 |
| artifactIntegrity | VERIFIED、MISMATCH、UNAVAILABLE、NOT_CHECKED | 摘要一致不等于内容真实 |
| anchor.status | not_requested、pending、confirmed、failed | 与 verdict、复验结论和运行状态独立 |

初始原因码至少涵盖 BLOCK_MISMATCH、FIELD_MISMATCH、PROOF_INVALID、SIGNATURE_INVALID、ATTRIBUTION_UNRESOLVED、UNSUPPORTED、RATE_LIMITED、TIMEOUT、BASELINE_CONFLICT、EVIDENCE_MISSING、RULE_UNSUPPORTED、BUDGET_EXHAUSTED、NO_ACCEPTABLE_DELIVERY、ARTIFACT_MISMATCH。A/B 在共享定义中区分验收原因与运行原因，C 显示对应中文及证据，不在前端重新推断。

旧包复验的一致性和对当前任务的适用性分开：原规则下可以复现，不保证当前服务版本、请求条件或信任策略仍接受它。

## 3. 包之间的函数边界

A 已实现 `verify_delivery`、`replay_evidence`、`fact_key`。`build_evidence` 的实际参数为 `(request, delivery, context, provenance)`，内部重做核验，输出 `{bundle, manifest}`，不接受调用者自报结果。B 的实际公开入口为 Engine.candidates/createRun/importEvidence/createReplay/observeRpc 与 HTTP API；表中的 B 函数名为职责映射，不是额外 SDK 别名。C publish_anchor 尚未实现，B 默认发布 not_requested。

| 函数 | 负责人 | 输入 → 输出／约束 |
| --- | --- | --- |
| `verify_delivery(request, delivery, context)` | A | 结构化输入 → VerificationResult；核心不自行联网、写库或发送交易 |
| `build_evidence(request, delivery, context, provenance)` | A | 内部实际核验 → `{bundle, manifest}`；规范化和摘要算法唯一实现 |
| `replay_evidence(bundle, manifest, context)` | A | 检查摘要并重跑原规则 → 完整性、重算结果、差异和未知项；不直接采用旧 result |
| `fact_key(bundle, context)` | A | 经核验事实的分组键；B 用于索引去重，不把摘要数量当信誉票数 |
| `find_service(task, constraints)` | B | 候选及排序理由；所用历史证据须已复验且适用 |
| `check_service(serviceId, task)` | B | 有界探测 → 观测，不返回伪造的确定性结论 |
| `verify_before_use(task, candidates)` | B | 调用服务并调用 A 的内核 → RunSnapshot；耗尽即停止 |
| `report_outcome(bundle)` | B | 先校验／复验后入索引；不接受任意调用者自报 PASS |
| `publish_anchor(manifest, target)` | C | 指定已配置目标 → AnchorReceipt；B 队列调用，默认不自动主网发布 |

非预期程序异常不得转换为 PASS。schema 无效属于输入错误；有合法输入但缺少核验依据属于结构化 UNVERIFIABLE。UI_MOCK 走独立演示适配器并显式标识，不能通过让真实内核固定返回成功来伪造。

## 4. 前后端最小 HTTP 接口

先用轮询，避免同时开发 SSE／WebSocket。API 前缀暂定 `/api`。

| 路由 | 输入／输出 | 负责方 |
| --- | --- | --- |
| `GET /api/services` | 候选能力、来源、窗口、指标和最近适用证据；最终排序随任务返回 | B |
| `POST /api/runs` | `{task, contextId, candidateIds?, useHistoricalEvidence?}` → `202 {runId, duplicate}`；重复输入复用任务，冲突输入 409 | B |
| `GET /api/runs/{runId}` | RunSnapshot，attempts 中含交付观测、VerificationResult 与 evidenceId | B |
| `GET /api/evidence/{evidenceId}` | manifest、完整性／复验状态、只读 bundle 下载入口、发布状态 | B |
| `GET /api/evidence/{evidenceId}/bundle` | 原始规范化证据正文，不能由前端重组后冒充原包 | B |
| `POST /api/replays` | `{evidenceId, contextId}` → `202 {replayId}`；contextId 必须来自配置 | B 调 A |
| `GET /api/replays/{replayId}` | ReplaySnapshot，含重算结果、比较和原因 | B |

请求体／schema 错误返回 400，资源不存在返回 404，重用 requestId 的冲突返回 409、拒绝的导入／证据返回 422，非预期故障返回 5xx；失败验收是合法业务结果，不以 HTTP 500 表示。POST 不接受客户端自报 verdict，也不接受未经允许的任意下载 URL。证据下载必须来自受控存储，后续远程获取增加协议、主机、大小和超时限制。

锚定写入暂由后台受控配置或本地脚本触发，C 从证据详情读取发布状态。P0 不暴露任意公众可花费维护者 Gas 的发布端点。

## 5. 四份最先交换的样本

| 样本 | 预期信息 | 关键检查 |
| --- | --- | --- |
| 正确交付 | PASS + VERIFIED + 全部必需检查通过 | 可生成带证据引用的事实卡 |
| 签名错块 | FAIL + VERIFIED + BLOCK_MISMATCH | 正确的旧区块证明仍可能不满足请求 |
| 签名错值 | FAIL + VERIFIED + FIELD_MISMATCH | 响应值与有效证明解码值对照 |
| 证据或归属不足 | UNVERIFIABLE + 明确未知项 | 不伪造绿色结论，不自动归责 |

G0 可交换无实际证明的 UI_MOCK 形状样本，G1 起逐步替换为实际运行输出。故障注入样本若包含真实证明并实际执行核验，可标 FAULT_INJECTION；它和 UI_MOCK 不是同一类材料。

## 6. 独立实例与信任配置

B 提供单独端口、数据库、证据目录与配置；A 的 CLI 和第二实例重新读取材料并执行校验，不能依赖第一实例的结论缓存。复验需要的基准／密钥策略由第二实例自行接受并配置，不能仅信任待验包自带的授权声明。

启动完成时固定 schemaVersion、ruleVersion、规范化库、签名域与样本版本。修改这些约定需要更新文档和样本，使三人的实现可以明确检测不兼容。

## 7. B 已落地的接线细节

- `RunSnapshot.accepted` 只有本次真实 PASS、候选身份匹配且预算内才能非 null。attempts 自身有 RUNNING/COMPLETED/INTERRUPTED 状态，RUNNING 时观测尚未定案；其中分别保存 observationStatus、runtimeReason、verification 与 evidenceId；运行生命周期不代替数据／归属结论。
- `GET /api/meta` 获取已配置 contextId 与公开任务参数；`POST /api/selection` 固定输入比较候选，不调用交付服务。服务列表和选择响应为 `{apiVersion,candidates}`。
- `POST /api/evidence/import` 接受 `{bundle,manifest,contextId}`，重新执行 A；不能传任意 context、URL、自报 verdict 或授权。GET `/api/evidence/:id/manifest` 配合 bundle 原字节下载。
- 复验 COMPLETED 不等于 PASS；读不到或存储文件已变的复验为 ERROR，并给 EVIDENCE_UNAVAILABLE／ARTIFACT_MISMATCH。上下文不同仍须通过额外报告一致性检查才允许导入／用于历史排序。
- `Publication` 增加 adapter、attemptId、attempts、attemptedAt、error；默认 not_requested/not_configured，无 txHash、无链上成功。C receipt 接入需另补真实链字段，现有 test_failure 不构成 C adapter 已完成。
- 同 requestId 的完整输入（包括选取选项）摘要原子登记，相同并发返回同 runId，采用与消费事务提交；崩溃不确定的旧调用停止，不自动重发。
- 原始观测为 `/api/observations`；有体积、目标与时间预算。C 默认 localhost/127.0.0.1:5173 可跨域调用，后端仅 loopback。本地联调不等于公开多租户部署。

完整字段与可执行调用示例见 [B 实现与复验](13-B包实现与复验.md)，公共类型以 `packages/protocol/src/index.ts` 为准。
